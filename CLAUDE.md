# Marktperspectief

A personal finance dashboard for one owner per deployment, on Vercel. Must be reachable from anywhere, so every page and endpoint that shows financial data needs auth. The owner's own context (the deployment, private plans and designs, their finances) is in `CLAUDE.local.md`, which is gitignored.

## Stack

- Next.js 16 App Router with Cache Components (`cacheComponents: true`), TypeScript, Tailwind 4, pnpm
- Drizzle ORM (stable 0.45 line, `casing: "snake_case"`) on Turso Cloud (libSQL, free Starter plan, Dublin) via `@libsql/client`; env `TURSO_DATABASE_URL` / `TURSO_AUTH_TOKEN`, used only on Vercel: `defaultConnection` in `src/db/connect.ts` picks Turso when `VERCEL_ENV` is `production` or `preview` and the local file DB `.data/dev.db` otherwise, so `next dev`, `drizzle-kit`, the scripts and a laptop `next build` never touch Turso, except `pnpm db:rebuild`, which only reads it. A preview reads production's database because libSQL opens a local file as soon as the module loads, and a Vercel build has none; only a production build migrates and seeds (`buildCommand` in `vercel.json`).
- A private Vercel Blob store (Dublin) for raw broker exports, the source of truth; Turso tables are rebuilt from them. Env `BLOB_READ_WRITE_TOKEN`. Files live at `<VERCEL_ENV or development>/raw/<kind>/<sha256>/<name>`, so local uploads land under `development/`. Without the token, as in a fresh clone or a script run without `--env-file`, `raw-store.ts` keeps them at the same paths under `.data/blob/`.
- Env vars come from Vercel: `vercel env pull` writes `.env.local`, and `.env.example` lists them. Never print or read secret values. `ownerDate` in `src/lib/dates.ts` gives today in `OWNER_TIME_ZONE`, Europe/Madrid when unset.
- Better Auth (`src/lib/auth.ts`): passkey-only, single owner account, named by `OWNER_NAME`. A passkey can be registered without a session only with `AUTH_SETUP_TOKEN`, in the form `/login?setup` shows, and only while the owner has none; `src/proxy.ts` redirects anonymous requests to `/login`, and data-loading components re-check the session, both through `isSignedIn`. Under `next dev` it lets in every request addressed to localhost, where `pnpm dev` listens. It is also the OAuth 2.1 server for the remote MCP endpoint: `mcp()` with `jwt()`, and `cimd()` accepting only client documents on claude.ai, so there is no open registration. Tokens carry the `portfolio` scope, and `/consent` asks for it after the passkey sign-in.
- Functions run in `dub1` (`vercel.json`), next to Turso and Blob
- Market data: Yahoo's `chart()` through `yahoo-finance2` (closes and dividends) and the ECB's reference rates. Vercel cron calls `/api/cron/daily` at 22:00 and 05:00 UTC with `CRON_SECRET`; it syncs, then `refreshDerived` rebuilds `portfolio_daily`; the MCP's `refresh_prices` does the same on request.
- `.github/workflows/preview-cleanup.yml` deletes the Vercel preview deployments of branches without an open PR, on every closed PR, with the repo secret `VERCEL_TOKEN` and the repo variables `VERCEL_SCOPE` and `VERCEL_PROJECT`; without `VERCEL_PROJECT`, as in a fork, it skips
- MCP: `src/mcp/server.ts` builds the tools, which `src/mcp/stdio.ts` serves to Claude Code on the local DB (`.mcp.json`) and `/api/mcp` to claude.ai behind `requireMcpAuth`, statelessly through `@modelcontextprotocol/server`. The protected resource and authorization server metadata come from the Better Auth handler, which `src/app/.well-known/[...path]` forwards to. The plugins and `auth` (the CLI) share one exact version: run `pnpm auth:schema` after an upgrade and check that no existing auth table changes.
- The draft card (`src/mcp/draft-card.ts`) is an MCP Apps view (`@modelcontextprotocol/ext-apps`, spec 2026-01-26): `add_transaction`, `propose_thesis` and `add_instrument` name it in `_meta.ui` and return their preview as `structuredContent` with its `kind`, and the card shows it with a Confirm button that calls the confirm tool through the client. On `/api/mcp` the confirm tools carry `visibility: ["app"]`, so claude.ai keeps them from the model and only the button saves (20 Nov 2026, instead of trusting the model to wait for a yes). Claude Code keeps app-only tools from the model too and draws no card, so `stdio.ts` builds the server with `modelConfirms`, which lists the confirm tools to the model and tells it to confirm after the user's yes, and Claude Code reaching `/api/mcp` can read but not save (23 Nov 2026, instead of telling the cases apart by the model's tool list, which assumed Claude Code ignores `_meta.ui`). The card speaks the protocol's JSON-RPC over postMessage itself rather than bundling ext-apps' `App`, half a megabyte for four messages, and `draft-card.test.ts` holds it to ext-apps' `AppBridge`. It takes the client's theme variables and writes every value with `textContent`.

## UI

- Swiss theme in `src/app/globals.css`, dark only. Tokens use shadcn's names (`--background`, `--primary`, `--muted-foreground`, `--border`, …) plus `--positive`, `--negative`, `--annotation`, `--logo-dot` and one per holding type (`--compounder` gold, `--bargain` blue, `--cigar-butt` tobacco, `--cyclical` violet, `--asset-play` rose, `--avoid` the red of a loss, on purpose, `--core` a light neutral); components use token classes, never raw colours.
- Archivo with its width axis (`font-stretch`) for condensed headings and numbers, the `.type-*` classes for the type scale, `text-note` for 13px notes, `tabular-nums` for figures.
- Square corners, no shadows, no boxed cards. Each section opens with a 2px foreground rule, without section numbers (10 Nov 2026); an active control is filled teal.
- Copy (10 Nov 2026): the owner is the only user, so nothing explains itself. No sentence under a heading, no note that repeats its label, no empty-state line where leaving the part out says enough (an empty page or chart keeps one), no key for a single series. The price date shows once, under Total value. Positions and totals are whole euros; prices and transactions keep their cents.
- Charts: `--chart-1` portfolio, `--chart-2` benchmark, `--chart-3` net invested, with the same meaning in every chart. Gains and losses always show a sign and an arrow, never colour alone: render them through `<Change>`.
- The chart's vs market view sets the portfolio's time-weighted return against the chosen benchmark's total return, both at 0% at the start of the range; the overview's Time-weighted KPI is the gap between the two (vs Stoxx 600). The portfolio counts gross dividends while the ETFs reinvest theirs after withholding, which flatters it slightly; the note that said so is gone (10 Nov 2026). The overview's annualised return also shows the same euros in the Stoxx 600, money-weighted: each day's net flow buys or sells index units, the flows net invested sums, so a fee is money put in rather than a sale of units (decided 28 Oct 2026, instead of the plan's fee as a withdrawal). A withdrawal the units can't cover sells them all. The chart shows no such amount in euros: the owner finds it demotivating and the chart says enough (30 Oct 2026).
- The overview and the chart are one section without a visible heading, the chart's controls between them. The overview shows the value, the total return (its parts behind an info icon), the money-weighted and time-weighted returns and the estimated dividends; the returns follow the chart's range, from the chart's first day in it, annualised for 1Y and longer and over the period for shorter ranges (30 Oct 2026). Below the holdings, which end with a totals row, come Dividends (received per year, then the next 12 months' estimate) and Options (open options with their result at the underlying's last close, finished ones collapsed).
- Net invested is the money put in less the money taken out: buys, fees and put buybacks, less sale proceeds, dividends and put premiums. Reinvested money cancels out, so the gap to the portfolio line is the total return (decided 27 Oct 2026, instead of the cost of the shares held). Broker cash isn't tracked, so cash waiting at a broker counts as taken out, and the line can dip below zero, which the chart shades without a key. The chart draws the line only when its checkbox is on, because it flattens the value line (30 Oct 2026), and the tooltip lists it and the gain only then.
- Logo: the Viewfinder, MP in teal corner brackets with an orange dot. `src/components/logo.tsx` has `Logo`, the full-width version with the name as Archivo outlines (width 125, weight 500, letter-spacing 0.12em), and `LogoMark`, the icon, which the header shows below `md`. The header is the logo, which links home, and two icons, Import and the privacy toggle; `IconLabel` names each and shows the name on hover or focus. The favicon (`icon.svg`, and `favicon.ico` on the background colour) is the mark redrawn on a 16 px grid, so it stays sharp at 16 and 32 px; `apple-icon.png` is the full mark.
- Every amount renders through `<Money>`, which the header's privacy toggle blurs (`blur-money`, which grows with the text): it sets `data-privacy` on `<html>` (the `private:` variant), and an inline script in the layout applies the stored choice before the first paint. Percentages and share prices stay visible.
- Pages are 1200px wide (`max-w-300`). Wide tables scroll inside their own box on a phone.
- Clicking a holding or a closed position opens its panel from the right at `/h/<instrument id>`. The home page's sections live in the `(home)` layout and the panel is that route's page, so opening or closing a panel never re-renders the portfolio, and a refresh keeps the panel open. Each link prefetches the panel's frame, so the sheet slides in at once while its data streams in; on hover or focus it also prefetches the data, which the page's session check and `loadHolding` allow by caching in the browser (`use cache: private`) for 30 seconds, the shortest stale time a prefetch can carry (30 Oct 2026). The links replace the URL instead of pushing it, and closing returns to `/`. The panel is a native `<dialog>` (`sheet.tsx`) rather than shadcn's Sheet, so it needs no Base UI.
- shadcn/ui (Base UI, `components.json`) supplies only the container and tooltip in `src/components/chart.tsx`, over Recharts 3.10; the rest of that file is the axis ticks and tooltip box both charts share. `shadcn init` and `shadcn add` rewrite `globals.css`, swap the font for Geist and add components and packages nothing uses: put the tokens back and remove what has no importer.

## Layout

- `data/`: the owner's local financial data (exports, notes). Gitignored, never commit it.
- `.data/`: the local dev database, the raw files without a Blob token (`blob/`) and the demo's files (`demo/`). Gitignored.
- `src/app/`: routes only: pages, layouts, route handlers, `globals.css` and Next's icon files. A page keeps its own data-loading section, behind `Suspense`; the home page keeps it in the `(home)` layout, so the holding panel can be a page below it.
- `src/components/`: UI with no domain knowledge (`Button`, `Table`, `Sheet`, `Segments`, icons, the logo, `<Money>`, `<Change>`, …), so swapping in a library changes one file. A component made of several files gets its own folder; single-file ones sit flat, shadcn's too (`components.json` points `ui` here).
- `src/features/<feature>/`: what a feature renders, and its server actions: `portfolio` (the home page's sections and the holding panel), `import`, `auth` (login and consent forms) and `site-header` (with the privacy toggle).
- `src/lib/`: the server side, shared by the app and the MCP tools: `engine/`, `portfolio/`, `market/` and `import/`, Better Auth (`auth.ts`, `auth-client.ts`) and the helpers they share (`dates.ts`, `format.ts`, `secret.ts`, and `schemas.ts`, which holds the chat entry and the MCP input so they share their fields; a schema with one reader lives next to it). Only `engine/` is framework-free.
- `src/lib/engine/`: pure portfolio math, with no `next`, `drizzle` or clock imports. `ledger.ts` replays trades into one FIFO book per instrument across brokers, throws on an oversell and returns each holding period that a full exit closes; `options.ts` folds sold puts into positions; `daily.ts` turns both into each day's value, flows and time-weighted return index; `dividends.ts` matches a payment to Yahoo's dividend and estimates a year of dividends; `benchmark.ts` turns a listing's closes and dividends into a total-return index on the portfolio's days; `simulate.ts` puts each day's flow into such an index instead; `xirr.ts` is the money-weighted annualised return, and its `annualised` turns a growth factor into a yearly rate. Amounts are integer cents and shares integer micro-shares (`money.ts`).
- `src/lib/portfolio/`: `ledger.ts`'s `loadLedger` turns the ledger tables into engine inputs, converting to euros at the ECB rate on or before each date, for `load.ts`, `refresh.ts`, `holding.ts` and the chat trade's preview. `load.ts`'s `loadPortfolio` gives the home page and the MCP `portfolio_summary` the overview figures, with the returns over each of the chart's ranges (`ranges` in `dates.ts`), the value series with net invested summed from the daily flows, the time-weighted return and both benchmarks' total-return indices, the money-weighted return of the same flows in the Stoxx 600, the holdings priced at their last close with each one's current thesis, the closed holding periods, the dividends received per year and the sold puts. Realised is the sells less the buys plus the cost still held, so partial sells count; over a range, the cost held at its start replaces the buys before it. `refresh.ts` writes the daily series up to the latest close, or to a later trade or cash flow, so a chat trade counts in the totals before its close; after an instrument's last close, or for one without closes or a Yahoo symbol, its trade prices stand in for closes, here and in `loadHoldings` alike (which reads each holding's last 100 days of closes), and here also before its first close; the cron, an upload that applies a file and a confirmed or undone chat trade call it. `holding.ts`'s `loadHolding` gives the panel one instrument's closes since its first trade, its trades, stock dividends and dividends, and its position or closed periods from `loadHoldings`, the part of `loadPortfolio` that prices the holdings.
- `src/lib/market/`: the Yahoo and ECB adapters and `syncMarketData`, which upserts closes, dividends and rates from 10 days before the last stored one, and fetches every listing in full, from 10 days before the first trade, while no dividend is stored; the ECB only when an instrument is in another currency.
- `src/lib/import/`: broker file parsers (`parsers/`, pure: text or sheet rows in, ledger rows out), ISIN resolution, and the pipeline: `ingestRaw` stores a file in Blob, then `applyRaw` reads the ledger, checks the file and writes its rows in one write transaction, with the supersede plan (`reconcile.ts`), so two applies at once can't both pass the oversell check. The `/import` page, the rebuild script and the chat tools call it; `/import` refuses a chat trade or its undo, which only the MCP writes.
- `src/lib/demo/`: an invented investor for a fresh clone and the public demo. `plan.ts` holds only dates and sizes: eight stocks and a monthly buy of a world ETF at DEGIRO since 2021, three sold Heineken puts and a thesis per holding type. `exports.ts` turns it into DEGIRO's two exports at the closes, dividends and USD rates in the database, so the trades sit on real prices, and a put is assigned when the close on its expiry is under the strike. `load.ts`'s `loadDemo` clears the ledger, applies the instruments file, syncs prices and imports the rest through `ingestRaw`. The public demo is a second Vercel project with its own Turso database and Blob store and `DEMO_MODE=1`: the login page shows "Enter the demo" instead of the passkey sign-in, a Better Auth endpoint (`/demo/sign-in`) that signs a visitor in as the owner without a passkey, and the daily cron reloads the demo instead of syncing, so visitors' changes last until the next run. Claude connects to the demo as to any deployment: with Claude's authorization request in the login page's query, the auth client sends it along with the demo sign-in, and the OAuth provider's hook carries it on to `/consent` (`auth.test.ts` follows it to a token `/api/mcp` takes). Both check `marker.ts`: the sign-in needs the demo's instruments file in `raw_imports`, the reload that or an empty database, so the setting on a real deployment does nothing.
- `src/db/`: Drizzle client (`connect.ts`), the generated Better Auth tables (`auth-schema.ts`), the ledger, market and derived tables (`schema.ts`), `getEffectiveTrades` (`ledger.ts`: not voided or superseded), the seed (`seed/`: the two benchmarks) and the tests' in-memory databases (`test-db.ts`, which adds the securities the tests trade).
- `scripts/`: laptop and build scripts, run with `tsx`.
- `src/mcp/`: the MCP server, its stdio entry, `chat.ts`, which adds, confirms and undoes a trade told in chat, proposes and confirms a thesis, and adds and confirms an instrument, and `draft-card.ts`, the card a preview shows as.
- `evals/`: scripted chats that a real model plays out against the MCP server on an in-memory portfolio (`harness.ts`, which seeds Exor at DEGIRO and Heineken at Saxo, sets today once per run, for the model and as the server's clock, to the last Tuesday to Friday, so no trade falls on a weekend, builds the server as `/api/mcp` (`card`) or `stdio.ts` (`chat`) does, lists the tools whose visibility includes the model, and leaves out `refresh_prices`, which goes online), each with a check on the tools it called, their input, the ledger and its replies (`cases.ts`); every case also checks that each confirm names a draft from an earlier turn. `pnpm eval` runs each case `EVAL_RUNS` times (3) and fails unless every run passes; it clears `BLOB_READ_WRITE_TOKEN` and works in a temporary folder, so confirmed entries' raw files stay out of Blob and the checkout.
- `.agents/skills/`: agent skills, each symlinked into `.claude/skills/` so Claude Code loads them on the laptop and in the cloud.

## Data model

- Dates are `YYYY-MM-DD` text and timestamps ISO text. Amounts are stored in the row's own currency, except trade costs, which are EUR in `transactions.fees_eur`.
- One instrument per security: a slug id and its current ISIN. An older ISIN is an `instrument_aliases` row, so an ISIN change or a listing move never splits a FIFO book. Holdings are data, not code: an instruments entry (`chat: "instruments"`, with instruments, aliases and corporate actions), uploaded as a JSON file on `/import` or written by the MCP's `add_instrument` and `confirm_instrument`, goes through `ingestRaw` like any import, so Blob keeps it and the rebuild replays instruments files before the rest. An entry upserts by id, and fails on an ISIN or Yahoo symbol that belongs to another instrument or an alias for an unknown one. The owner's own instruments file lives outside the repo (17 Nov 2026, for open-sourcing).
- Benchmarks are `benchmarkIds` in `load.ts`: `SXR8.DE` for the S&P 500, and `EXSA.DE` for the Stoxx 600 with its dividends reinvested, because Yahoo's history of Amundi's Stoxx 600 ETF (`MEUD.PA`) starts only on 19 Feb 2024.
- `price_daily` holds raw closes: the Yahoo adapter undoes Yahoo's split adjustment. Yahoo can book a bonus issue as a split while the ledger has it as a stock dividend, so Yahoo's splits only ever correct prices, never share counts.
- An instrument without a Yahoo symbol is valued at its own trade prices, and the sync lists it: a security Yahoo no longer has, or one whose history Yahoo adjusts for a split it does not report.
- `source` is where a row came from (a broker file or chat), `broker` is where the shares are held. A move between brokers is a `transfer_out` and a `transfer_in` transaction: it changes per-broker share counts (dividend entitlement) and never touches FIFO lots.
- libSQL enforces foreign keys by default, so delete child rows before their `raw_imports` row. Instruments are never deleted, which keeps price rows attached.
- Each uploaded file is a `raw_imports` row keyed by its SHA-256, so the same file applies again only once `parserVersion` in `src/lib/import/ingest.ts` has gone up: bump it when a parser reads more of a file, then upload the file again. Rows already in the ledger (same source or broker and external key) are skipped and counted as duplicates, so an overlapping export or an upgraded parser only adds what is new; a parser that keys its rows differently needs a migration that deletes the rows it wrote (`0012` does it for the statements' income and fees). A file with any error writes only its `raw_imports` row, with the errors in `report`: an unknown ISIN, or trades, voids or stock dividends that would sell more shares than are held. The Binck CSV is a one-off format, normalised by hand from Binck's PDF statements and checked line by line, so its parser only maps columns.
- DEGIRO's Transactions export: option rows (exchange `LFF`) are sold puts, in `option_trades`. The product name (`HEI P70.00 20DEC24`) gives the strike, the expiry and an `option_code` alias for the underlying, whose prices value the put. A put row at price 0 closes the put: assigned when that day has a buy of 100 shares per contract at the strike, expired otherwise. Only euro puts are read, and a call is an error. Other rows at price 0 (rights) are skipped. A sell and a buy without an order ID at the same date, time, quantity and price are a non-cash move, such as an ISIN change or a listing move, and are dropped. New shares from a rights issue are booked under the rights' ISIN, so that ISIN is an alias of the security.
- DEGIRO's Account statement (Spanish descriptions) gives the cash lines the Transactions export lacks. Its trade lines and DEGIRO's costs on them (`Costes de transacción`, with an order ID) are skipped: the Transactions export has them, and both sum to the same fees. Each line is its own row, keyed by its booking date and time, value date, ISIN, description and amount, so a later statement adds a correction to the lines already stored; a withholding line has no gross. The French transaction tax is a fee rather than part of the order's `feesEur`, because the statement can't change rows another file wrote; total return is the same either way. Connectivity fees, interest, the option exercise fee and DEGIRO's refunds are fees too, and securities lending is income. A wrapped description continues on a row with an empty date. Any other line is an error.
- Income is gross in every figure: Binck and DEGIRO book gross and withholding. `payments` sums a payment's lines per broker, instrument, value date, kind and currency, lines without a gross apart, so a reversal and rebooking nets out; a dividend booked only net is then grossed up in `euroIncome` from `dividend_events` (Yahoo's dividend per share, before its split adjustment) times the shares held at that broker the day before the ex-date (decided 27 Oct 2026, instead of the plan's event matching), and stays net when Yahoo has no dividend in the 60 days before the payment. The overview's dividends include Binck's and DEGIRO's lending income.
- A put's premium is its own income line, net of buybacks and fees, and assigned shares are held at the strike, as DEGIRO books them (decided 27 Oct 2026). In the daily series a premium is paid out like a dividend, a buyback is money in, and an open put counts against the value at what it is in the money.
- Saxo's Transacties export (xlsx, Dutch): only `Transactie` rows (buys, sells, transfers in from Binck) are read. Saxo books corporate actions without a share count, so their share changes go in an instruments file, with the counts worked out from the trades. A stock dividend adds shares at no cost. Each cash line is its own row, which `payments` sums, so a correction joins its dividend: a cash dividend is booked net and grossed up from Yahoo, while capital repayments, choice and scrip dividends carry no withholding; cash for fractions is a fee credit, and interest or custody a fee.
- A trade told in chat is a buy or sell at DEGIRO or Saxo of a security the ledger knows. `add_transaction` checks it (no future date, no sell of more than is held; a price over 15% from the close and a similar trade within 3 days are warnings) and keeps it in `chat_drafts` for 30 minutes without touching the ledger. `confirm_transaction` (the card's Confirm button, or the model after the user's yes) writes it through `ingestRaw` as a chat entry (`raw_imports` kind `chat`, keyed by the draft id, so a repeat is a duplicate), and `undo_chat_transaction` writes a void entry that sets `voided_at`. Chat dividends are left out: every broker's export books them.
- A thesis is a holding's type (`holdingTypes`: compounder, bargain, cigar butt, cyclical, asset play, avoid, core), two to four pillars each with what would prove it wrong (avoid needs none) and the reason for the type or for what changed, told in chat. `propose_thesis` keeps it in `chat_drafts` like a trade, and `confirm_thesis` writes it through `ingestRaw` as a chat entry, so Blob keeps it and the rebuild replays it. A thesis is never edited: a new one replaces the holding's current one, the newest by id. The holdings table shows the type and the panel the thesis, both through `HoldingType`, a badge outlined in the type's colour with a 12% tint (never filled, which means an active control); the panel cuts the reason at three lines (`Clamp`). Core is an index fund held for good, sold only to move into a cheaper or tax-better fund (10 Nov 2026).
- A chat trade counts until its broker's export has the order: `planSupersede` pairs it with that order's fills summed, at the same broker, instrument, side and quantity, within 3 days and 2% of their average price, the closest date first, and sets `superseded_by` to `<broker>:<order ref>`. It runs on every apply of a file with trades, so the trade's own confirm, a later export and the rebuild all pair it the same way. An export whose trades at that broker start on or before a pending chat trade's date and run more than 3 days past it, without pairing it, fails: undo the chat trade, then upload the file again. A superseded trade can't be undone.

## Commands

- `pnpm dev`, `pnpm build`, `pnpm lint`, `pnpm typecheck`, `pnpm test` (Vitest, colocated `*.test.ts`)
- `pnpm format` runs Biome, the formatter only (4-space indent from `.editorconfig`, 120 columns, import order), then ESLint's `padding-line-between-statements`: a blank line after declarations, around blocks and before `return`. `pnpm lint` checks both, so CI does. The ESLint rule is deprecated in core; move it to `@stylistic/eslint-plugin` when upgrading to ESLint 11.
- drizzle-kit's turso dialect drops a column named in a foreign key with a plain `DROP COLUMN`, which libSQL rejects: recreate that table in the migration instead (`0009` does it for `fees` and `corporate_actions`).
- `pnpm db:generate` writes a SQL migration to `drizzle/`, `pnpm db:migrate` applies it to the local DB and then runs `pnpm db:seed` (upserts the instrument seed), `pnpm db:check` validates the migration files, `pnpm db:rebuild` replaces the local DB's ledger tables with the seed and production's raw files from Blob, instruments files first and then oldest upload first, retrying the files that fail until a pass applies none, then checks that its ledger tables match production's and refreshes its daily series, `pnpm db:sync` fetches prices and ECB rates into the local DB and refreshes its daily series, `pnpm db:demo` migrates the local DB and replaces its ledger with the demo (it needs Yahoo and the ECB) and writes the demo's files to `.data/demo/`, `pnpm db:studio` opens Drizzle Studio on the local DB. Avoid `drizzle-kit push`: it hangs on an interactive prompt.
- Production migrates and seeds during the Vercel production build (`buildCommand` in `vercel.json`), so a migration reaches Turso only when its PR is merged to `main`.
- The local DB starts empty: run `pnpm db:migrate`, or `pnpm db:demo` for a full dashboard. `.env.example` lists the env vars, none of which a local run needs. Local dev needs no passkey.
- `pnpm auth:schema` regenerates `src/db/auth-schema.ts` after changing Better Auth plugins
- `pnpm mcp` runs the MCP server on stdio (Claude Code starts it from `.mcp.json`)
- `pnpm eval` runs the evals with `ANTHROPIC_API_KEY`, against `EVAL_MODEL` (`claude-sonnet-5-5` when unset), optionally only the cases whose name contains `EVAL_CASE`. `.github/workflows/evals.yml` runs them on PRs that touch `src/mcp/`, `src/lib/schemas.ts`, `evals/`, the lockfile or the workflow, with the repo secret `ANTHROPIC_API_KEY` (without it, as in a fork, it skips), and by hand against any model; it writes the results table to the job summary.

## Context

- This file holds the project's rules and decisions, and `CLAUDE.local.md` the owner's own context. Neither goes in Claude's auto memory (turned off in `.claude/settings.json`). `CLAUDE.local.md` exists only where the owner keeps it, so a session without it asks the owner.
- Work in small agreed steps: finish what was asked, then propose the next step and discuss before building more. Don't start servers or add features without a go.
- No noise or redundant tests and comments, ever. Each test and assertion must catch a regression that no other one catches, in something production code reads; each comment must say what the code, its names, the tests and these docs don't. Fewer, sharper tests beat coverage.
- Each change is one PR from a branch; CI (`.github/workflows/ci.yml`) runs typecheck, lint, `db:check` and tests on every PR.
